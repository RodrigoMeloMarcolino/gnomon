# Fase 00.5 — Hardening de nascimento: lições do Moira (docs-only)

Status: done (concluída em 2026-07-23, junto da criação — aplicação imediata das emendas)

## Objetivo

Auditar specs, ADRs e tasks contra a lista de dívidas de negócio e estrutura do Moira
(avaliação completa do repositório `../moira` em 2026-07-23) e aplicar as correções na
documentação **antes** de escrever código de negócio — o Gnomon nasce pagando por design as
dívidas que o Moira pagaria por refatoração. Fase docs-only: nenhum código novo.

## Contexto

O Gnomon já codificava várias lições (tenant acima de calendários, Keycloak, constraint de
double booking, transação curta, ArchUnit, envelope de erro). A auditoria encontrou 12 dívidas
do Moira ainda não blindadas explicitamente. Esta fase as fecha.

## Matriz de rastreabilidade dívida Moira → artefato Gnomon

| # | Dívida Moira (evidência) | Correção Gnomon | Artefato |
| - | ------------------------ | --------------- | -------- |
| 1 | Regra `09:07` aceita na escrita → 500 no `available-slots` (validação assimétrica) | Validação simétrica: invariante de leitura = validação de escrita + CHECK | ADR 0016; spec booking §3 (`availability_rules`); task 03 |
| 2 | CHECK constraints viravam 500 (sem handler) | Toda constraint nomeada tem tradução 4xx determinística; tabela viva por spec; verificação na fase 09 | ADR 0016; spec booking §6.1; spec multi-tenancy §7.1; task 04 |
| 3 | `updated_at` nunca atualizado (auditoria falsa) | `updated_at` só existe com trigger de banco | ADR 0017; spec multi-tenancy (nota de emenda); spec booking §3 |
| 4 | FKs sem índice (`appointments.provider_id` etc.) | Índice em toda FK na mesma migration | ADR 0017; specs booking/multi-tenancy (DDLs) |
| 5 | `status` de appointment como string livre | `CHECK IN (...)` + máquina de estados documentada | ADR 0017; spec booking §3; task 07 |
| 6 | Colunas mortas (`cancel/reschedule_token_hash` sem fluxo) | Colunas nascem na migration aditiva da fase 08 | ADR 0017; spec booking §3; tasks 04/08 |
| 7 | Segundos truncados silenciosamente no booking (`09:00:45`→`09:00`) | Rejeição 422; nunca truncar | ADR 0016; spec booking §5.2; task 04 |
| 8 | `Idempotency-Key` opcional → duplicidade em retry após timeout | Header obrigatório (422 na ausência); coluna NOT NULL | ADR 0014 (emenda); spec booking §3/§5.2; task 04 |
| 9 | Corrida com mesma idempotency-key sem teste | Teste de concorrência obrigatório (uma cria, outra faz replay) | spec booking §7; task 04 |
| 10 | Cache invalidado no dia errado (data do payload ≠ data local do provider) | Chave/invalidação derivadas da data local do calendário, mesma derivação da leitura | task 05 |
| 11 | E-mail sem normalização → contas duplicadas por case | `CITEXT` + lowercase no JIT provisioning | spec multi-tenancy §3.1; spec keycloak-auth §4 |
| 12 | Listagem admin sem paginação | Paginação obrigatória como critério de aceite | task 07 |

Dívidas estruturais já cobertas pelo desenho atual (sem emenda necessária): ORM vazando para
use cases (ADR 0002 + ArchUnit), god composition root `deps.py` (DI por módulo), ausência de
gates de arquitetura/CI (fase 09), `confirmed_phone=True` falso (confirmação de telefone fora
do MVP; `phone_verified_at` removida até a fase que a implementar).
